The problem

The division office needed answers to simple questions. How many teaching and non-teaching staff do we have, and in which schools? Which equipment is unserviceable or due for disposal? Of the computers delivered under the DepEd Computerization Program (DCP), how many still work? Which schools pay for internet, and are they getting the speed they pay for?

The answers existed, but they were scattered across each school's records, paper forms and people's memory. There was no single dataset anyone could query.

Gathering the data in the field

We collected it in person. Our team visited the schools and encoded each one's data into the division's standard workbook: one file per school, with sheets for personnel, equipment and internet connectivity. Where records were incomplete, the school's HR staff shared internal documents and employees' Personal Data Sheets, the government's standard employee profile form, so we could fill the gaps.

By the end there were 46 workbooks: one per school, plus one for the division office itself.

Field collection gets data that exists nowhere else, but it has a predictable side effect: many hands, many habits. The same position was typed as TEACHER I, Teacher I and T I. Phone numbers came with spaces, dashes or neither. Excel quietly added apostrophes in front of numeric IDs. Some people were encoded twice. I designed the pipeline around that reality instead of hoping the files would arrive clean.

Architecture

The system has four stages. Data only moves forward, and the original school workbooks are never modified.

Keeping the middle layer in Excel was deliberate. The offices already lived in spreadsheets, so anyone could open the consolidated files, filter them and check the numbers without the dashboard. That made it easy to trust what the dashboard showed, because every figure could be checked by hand.

Ingestion: 46 files that look alike but aren't

Every school used the same template, which helps, but templates drift once people fill them in. The ingestion script follows four rules:

  • Scan, don't list. It reads every .xlsx file in the source folder. Adding a school means dropping its file in and running the script again, with no code change.
  • Name from the file. The school name comes from the file name (Sample_Elementary_School.xlsx becomes "Sample Elementary School"), so every row has exactly one, consistent school label.
  • Read by position. The template has a two-row header, so data starts on the third row and columns are mapped by position, not by header text that people sometimes edit.
  • Rebuild from scratch. Each run regenerates the output completely. The same inputs always give the same output, so re-running never double-counts anyone.

Cleaning and data quality

Hand-encoded data fails in predictable ways, so each problem got an explicit rule:

FieldWhat we sawRule
PositionTEACHER I, Teacher I, T I, HT III, MT I, typosA lookup table maps every variant to one official title, such as Teacher I, Head Teacher III or Master Teacher I
NamesSome in all capsTitle case
Mobile numberSpaces, dashes, local and international formatsDigits only, one international format (+63)
Employee IDA leading apostrophe from Excel text cellsStripped, so IDs match across files
EmailMixed case, stray spacesLowercased and trimmed
Date hiredMixed date formatsParsed and written in one format

The most important rule is what happens to values the script doesn't recognize: it never guesses. An unmapped position goes to a Data Issues sheet in the output workbook, a person decides what it should be, adds it to the lookup table, and the next run fixes it everywhere. The Data Issues sheet has three sections: duplicate IDs, unmapped positions and other warnings.

The headcount that didn't add up

For the division office's own workbook, the script reported 143 people, and a manual count disagreed. Instead of adjusting the number, I traced it row by row.

Twenty-two employee IDs appeared twice in the same sheet: the same person, encoded in two places. The real headcount was 121. The template's 9999 separator rows had also been inflating manual counts, which is why the script skips them.

The fix was a rule rather than a one-off correction: keep the first occurrence of each employee ID, skip later copies, and list every duplicate with both row numbers so the office can correct the source file.

# Simplified: duplicates are reported, never silently dropped
first_seen, clean, issues = {}, [], []
for rec in records:
    first = first_seen.setdefault((rec["School"], rec["Employee_ID"]), rec["Source_Row"])
    if first != rec["Source_Row"]:
        issues.append(("Duplicate ID", rec["School"], rec["Employee_ID"],
                       f"rows {first} and {rec['Source_Row']}"))
        continue
    clean.append(rec)
The principle: every number on the dashboard can be traced back to a row in a source file, and every row the pipeline didn't use is listed with the reason.

Internet connectivity data

The internet data had more moving parts. Each school workbook records its connectivity, its ISP accounts, speed test results and subscription costs on separate sheets. A second script follows the same pattern and writes Merged_ISP.xlsx with five sheets: ISP accounts, speed test results, subscription cost, a connectivity summary and a per-school summary.

Speeds and costs arrive as text about as often as numbers, so every numeric column goes through pd.to_numeric(errors="coerce"). A cell like "20 Mbps" or "N/A" becomes empty instead of crashing the run or quietly turning into zero, and empty values are counted, not hidden.

The serving layer

The dashboard is a Streamlit app that reads the three consolidated workbooks. Loading goes through @st.cache_data, so the files are read once and every filter afterwards is instant.

Some of the most useful fields don't exist in the source data, so the app derives them on load:

  • Staff type. The source has no teaching or non-teaching column, so a position containing Teacher, Principal or Head counts as teaching staff, and everything else as non-teaching.
  • DCP equipment. An item counts as DCP ICT equipment when it has a DCP package value and isn't marked as non-DCP. Writing that definition down took a conversation with the people who manage the inventory, not just code.
  • Hire month. Hire dates are parsed tolerantly and grouped by month for the hiring timeline. Unparseable dates are excluded from the chart and still counted in the totals.

Access by role

The dashboard started as two separate prototypes: the four-module analysis app, and a landing page with sign-in. I merged them into one app with a three-step flow (landing, sign-in, dashboard) held in Streamlit's session state.

Access is a map from role to modules. HR sees Personnel. Supply sees Equipment and DCP ICT. ICT staff and the administrator see everything. After sign-in, the app builds only the tabs a role may open and loads only the files those tabs need. The HR view never reads the equipment file at all. That's least privilege applied to data loading, and it keeps memory use down as a bonus.

Disclaimer: sign-in is a simple in-app check suited to an internal deployment, not production-grade authentication. Replacing it with proper identity management is first on the list below.

What broke

"It works on my machine"

The first version pointed at a hard-coded Windows folder. On another computer it failed immediately with a file-not-found error. The fix was to keep the data files next to the app and use relative paths. The lesson was bigger than the fix: where the data lives is configuration, not code.

Charts that were confidently wrong

Two pie charts in the ISP module showed 100% "No": no school had an ISP subscription, and none had enough bandwidth. Nothing errored. The chart counted "Yes" values in columns whose names or values didn't match what the consolidation script actually wrote.

This was the most useful bug of the project. Between any two stages of a pipeline there's an unwritten contract: these column names, these types, these allowed values. When one side changes, nothing crashes; the dashboard just quietly lies. The diagnosis was to print the actual columns and values on load and compare them with what the chart expected. The lasting fix is to check that contract on every load and fail loudly when it breaks.

Results and what's next

46field-collected workbooks consolidated
3curated datasets with data-quality reports
4dashboard modules, gated by role
3offices using it: HR, Supply, ICT

The dashboard is deployed internally and used by the HR, Supply and ICT offices. Adding a school means dropping in one file and running the scripts again. Data problems are surfaced in the output instead of disappearing into a total.

If I rebuilt it today, these are the changes I'd make, in order:

  1. Validate at entry. Replace free-typed fields with dropdowns or a form, so T I can't be entered in the first place. Cleaning after the fact is the expensive place to fix data.
  2. A database in the middle. SQLite or PostgreSQL tables with an employee ID key would make duplicates impossible instead of reported.
  3. Schema checks between stages. Assert column names, types and allowed values on load, so the "100% No" bug becomes an error message.
  4. Real authentication. Hashed credentials or single sign-on, with roles managed outside the code.
  5. Scheduled refresh. Run the consolidation on a schedule instead of by hand.
  6. A public demo. The same app on synthetic data, so anyone can try it without seeing internal records.

How I worked

I built this with an AI coding assistant as a pair programmer. My part was the part a tool can't do on its own: collecting the data in the field, defining the business rules (what counts as teaching staff, what counts as DCP equipment, what to do with a duplicate), deciding how bad data should be treated, and checking every output against the source files until the numbers reconciled.
