e-QUAART

Assessment results management, analytics and intervention tracking for a schools division

The problem

Schools run several reading and math assessments (CRLA, Phil-IRI, RMA, ELLNA, end-of-term). The results live in separate spreadsheets, so nobody can see learning gaps across classes, schools and the division, or tell whether an intervention actually worked.

How data moves through it

  1. Capture: grid + CSV/Excel import
  2. Quality check: submit → verify → return
  3. Classify by performance level
  4. Find learning gaps
  5. Intervene
  6. Reassess

Data engineering decisions

  • Validation at the door. Every import and form is checked against a schema before it touches the database, and a verification queue keeps unchecked results out of the analytics.
  • Rules as configuration. Performance levels, curriculum and who encodes what are settings, not hard-coded logic, so new instruments don't need a code change.
  • Idempotent year-end rollover. Moving learners into the next school year can be re-run safely without moving anyone twice.
  • Storage sized to the user. A single-file SQLite build runs on a school laptop with no admin rights; a PostgreSQL branch handles division-wide concurrent writes.
  • Privacy by design. Role-scoped access for 10 user types, a full audit trail, and a Data Protection Officer view for exports, retention and breach records.

School Division Dashboard

One Streamlit app over a school division's Excel records: personnel, equipment, DCP ICT equipment and ISP accounts

The problem

Simple questions (how many staff, which equipment is unserviceable, which schools have weak internet) meant opening four separate workbooks. Each office also needed to see only its own records.

How data moves through it

  1. Excel workbooks
  2. pandas: clean + flag
  3. Plotly charts
  4. Role-based Streamlit tabs
  5. CSV export

Data decisions

  • Clean on load. Text trimmed, blanks filled, cost and speed columns made numeric, dates parsed, so totals and charts don't break on messy cells.
  • Business rules as derived fields. An item counts as DCP ICT when it has a package value and isn't marked Non-DCP; teaching vs non-teaching staff is derived from position title because the source has no such column.
  • Least-privilege loading. After sign-in the app builds only the tabs a role may open, and loads only that role's files. Reads are cached.

Why data engineering

I've documented how data should move. Now I build it.

After graduating I kept landing in the same place: the spreadsheet nobody trusted. At DepEd and TESDA I was the one cleaning and reconciling it by hand. As a Business Analyst I write the rules, integration matrices and test plans that describe how data should flow between systems.

Data engineering is the next step on the same path: building that movement myself, tested and automated. I bring the habits engineers usually learn later: asking why the data is needed, agreeing on definitions, and proving the numbers reconcile.
