e-QUAART

Assessment results management, analytics and intervention tracking for a schools division.

The problem

Schools run several reading and math assessments (CRLA, Phil-IRI, RMA, ELLNA and end-of-term tests). Results sat in separate spreadsheets, so nobody could see learning gaps across classes, schools and the division, or tell whether an intervention had worked.

How data moves through it

  1. Capture: grid entry, CSV and Excel import
  2. Verify: submit, check, return
  3. Classify by performance level
  4. Find learning gaps
  5. Intervene
  6. Reassess

Data decisions

  • Validation at the door. Every import and form is checked against a schema before it reaches the database, and a verification queue keeps unchecked results out of the analytics.
  • Rules as configuration. Performance levels, curriculum and who encodes what are settings, so a new assessment needs no code change.
  • A rollover you can re-run. Moving learners into the next school year is idempotent: running it twice never moves anyone twice.
  • Storage sized to the user. A single-file SQLite build runs on a school laptop without admin rights. A PostgreSQL branch handles division-wide concurrent writes.
  • Privacy by design. Role-scoped access for 10 user types, a full audit trail, and a data protection officer view for exports, retention and breach records.
Demo data
~79,000 results, ~2,600 learners, ~1,400 interventions, 9 schools over 3 school years. All fictional.
Stack
TypeScript, Node.js, Express, Prisma, SQLite, PostgreSQL, React, Recharts
Quality
Unit and integration tests against a seeded dataset, type checks, and CI on GitHub Actions

One laptop with Node.js, or Docker Compose for a server

School Division Dashboard

One Streamlit app over a school division's Excel records: personnel, equipment, DCP ICT equipment and ISP accounts.

The problem

Simple questions (how many staff, which equipment is unserviceable, which schools have weak internet) meant opening four separate workbooks. Each office also needed to see only its own records.

How data moves through it

  1. Excel workbooks
  2. pandas: clean and flag
  3. Plotly charts
  4. Role-based tabs
  5. CSV export

Data decisions

  • Clean on load. Text trimmed, blanks filled, cost and speed columns made numeric and dates parsed, so totals don't break on messy cells.
  • Business rules as derived fields. An item counts as DCP ICT when it has a package value and isn't marked Non-DCP. Teaching vs non-teaching staff is derived from the position title, because the source has no such column.
  • Least-privilege loading. After sign-in the app builds only the tabs a role may open and loads only that role's files. Reads are cached.
Sources
4 Excel workbooks
Users
4 roles: HR, Supply, ICT and admin
Stack
Python, pandas, Streamlit, Plotly
Why private
It runs on internal records, so code and data aren't public. A synthetic-data demo is planned. Sign-in is a simple in-app check suited to an internal prototype, not production authentication.

Why data engineering, and what I bring

After graduating I kept landing in the same place: the spreadsheet nobody trusted. At DepEd and TESDA I was the one cleaning and reconciling it by hand. As a Business Analyst I now write the rules, integration matrices and test plans that describe how data should move between systems.

Data engineering is the next step on the same path: building that movement myself, tested and automated. I bring habits engineers often learn later: asking why the data is needed, agreeing on definitions, and proving the numbers reconcile.
